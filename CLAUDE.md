# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Glue around a self-hosted `supermemory-server` binary (installed separately into `~/.supermemory/bin` or `~/.local/bin`). Embeddings default to the server's built-in local ONNX model `Xenova/bge-base-en-v1.5` (768d, English-only; hooks translate non-English text first, see Translation below), or a multilingual 9router model (`openai-compatible`, e.g. `jina/jina-embeddings-v4`). LLM calls go through the local **9router** OpenAI-compatible gateway (`127.0.0.1:20128`). This repo adds lifecycle hooks so Claude Code, Antigravity and OpenCode share persistent memory **per project**. It is TypeScript run directly by **Bun** (no build step; runtime has zero dependencies, devDependencies are only types + `tsc`). Bun-only APIs are used (`Bun.spawnSync`, `Bun.stdin`, `Bun.serve`, `import.meta.dir`), so don't run it with node. README.md is in Indonesian.

## Commands

```bash
bun install                     # devDependencies only (types, tsc, prettier)
bun run start                   # bin/stack.ts: 9router (kickstart only if not answering) → LaunchAgents com.supermemory-local.{llm-proxy,zed-adapter,server} (RunAtLoad, KeepAlive) → mcpm-gateway (gateway.sh start); refuses if a memory/gateway port is held by another process
bun run stop                    # gateway → memory components; 9router keeps running; waits until unloaded and ports free
bun run restart                 # stop then start, memory components only (gateway untouched; not kickstart -k: the new process can race the old one's port)
bun run start|stop|restart --memory|--gateway|--9router|--all   # selectors combine; a typo exits 2 before touching anything
bun run logs                    # tail memory logs, gateway logs and 9router's /tmp logs
./scripts/run.sh <server|llm-proxy|zed-adapter>  # one component in the foreground, same config as launchd (bun run stop --memory first)
bun run status                  # exit 0 only if memory API and LLM proxy answer; also reports 9router, the gateway (servers.yaml), per-agent hook activity, OpenCode plugin load failures, extraction failure rate and the effective config (never changes the exit code)
bun run link-projects [--apply] # seeds data/projects.json so clones of one remote that already hold memories share them; dry run by default, reads the store, never writes to it
bun src/config.ts --shell       # the exports scripts/env.sh evals (every setting and its default lives in src/config.ts)
bun test                        # unit tests (src/*.test.ts); single test: bun test -t "stripContext"
bun run typecheck               # tsc --noEmit
bun run format                  # prettier --write . (config: prettier.config.ts extends @irfnd/prettier-config: tabs, single quotes, printWidth 130, organize-imports)
bun run format:check
bun run test-memory             # integration check; needs a running server; writes under <containerTag>_selftest, exits 1 on failure
bun run sessions                # Sessions UI on 127.0.0.1:20131 (SESSIONS_UI_PORT), foreground only: needs a TTY for the y/N approvals
bun run install-hooks [all|claude-code|antigravity|opencode]
bun run uninstall-hooks [all|claude-code|antigravity|opencode]
```

To exercise a hook by hand, pipe the agent's payload to the entrypoint:

```bash
echo '{"cwd":"/some/repo"}' | bun --env-file=.env bin/supermemory-hook.ts claude-code start
echo '{"cwd":"/some/repo","tool_name":"Edit","tool_input":{"file_path":"x.ts"}}' | bun --env-file=.env bin/supermemory-hook.ts claude-code change
```

Logs: hooks go to `~/.supermemory-hook.log` (home directory, shared by every agent and project, never rotated; filter with `grep agent=antigravity`), the server to `data/supermemory.log`, the LLM proxy (status and duration per call) to `data/llm-proxy.log`, the Zed adapter to `data/zed-adapter.log`, 9router to `/tmp/9router.log` and `/tmp/9router.error.log` (its plist's `StandardOutPath`/`StandardErrorPath`), and mcpm-gateway to `$MCPM_GATEWAY_DIR/logs/gateway.{stdout,stderr}.log`.

## Architecture

**Flow:** agent hook → `bun --env-file=<repo>/.env bin/supermemory-hook.ts <agent> <action>` → `src/agents/<agent>.ts#parse` (agent payload → one `HookEvent`) → `src/hook-handler.ts#runHook` (core handlers) → `SupermemoryClient` (HTTP to `SUPERMEMORY_API_URL`, default `:6767`) → `adapter.render` (stdout in the agent's format).

- **Actions** (five, with aliases in `src/agents/index.ts`): `start|check|context` recalls memories and prints the context block; `sync|prompt` prints only documents newer than the session's marker (`$TMPDIR/supermemory-sync/<session>`, written by `start`/`sync`) and not written by that same session (`metadata.session`), plus a hybrid search on the prompt (see Recall below), falling back to a full `start` when there is no marker yet; `change|observation` stores a tool or file-change note; `stop|session-end|summarize` stores the last assistant reply (truncated to 4000 chars); `compact|compacted` stores the agent's own compaction summary as a `session_summary` (capped at 40000 chars). When each agent fires them:
  - **Claude Code:** `SessionStart`→start, `UserPromptSubmit`→sync, `PostToolUse`→change, `Stop`→stop, `PostCompact`→compact (summary = last `isCompactSummary` transcript entry, trimmed by `trimCompactSummary`).
  - **Antigravity (agy):** `SessionStart`→start (one persistent `systemMessage`), `PreInvocation`→sync, `PostToolUse`→change, `Stop`→stop. `PreInvocation` fires before every model call; the adapter acts only when `invocationNum === 0` (first call of a user turn) and returns `null` otherwise, so a conversation holds one full block plus small updates. `Stop` has no reply text: the adapter reads the last `PLANNER_RESPONSE` of `transcriptPath` (`transcript_full.jsonl`; `transcript.jsonl` truncates content) and only when `terminationReason === 'NO_TOOL_CALL'`. Session id = `conversationId`, prompt = `lastUserInput`. No compaction hook. Hooks run synchronously and block the agent loop, so keep them cheap.
  - **OpenCode v2:** the plugin (`src/opencode-plugin.ts`) spawns this same hook: `session.hook('prompt')`→start/sync, `session.hook('context')` injects the cached blocks into `system` (no spawn: it runs once per model request), `tool.hook('execute.after')`→change, event `session.execution.succeeded`→stop (reply read through `ctx.session.context()`), `session.compaction.ended`→compact (summary = the `summary` string of the newest `compaction` item from `ctx.session.context()`, see `fixtures/opencode/08-compaction.json`; verified with `POST /api/session/{id}/compact`). The shell tool is named `shell`.
- **Per-agent knowledge lives only in `src/agents/<agent>.ts`** (`parse(raw, action) → HookEvent | null`, `render(context) → string | null`) with the read-only noise filters (`READONLY_CMD` in `agents/shared.ts`, OpenCode's read-tool set, Antigravity's `view_`/`read_` prefix). `src/agents/fixtures/` holds payloads captured from the real agents; `agents.test.ts` runs them as contract tests. When an agent changes its payload, refresh the fixture first. Unknown agent names get Claude Code's shape. The working directory comes from `cwd` (agy falls back to `workspacePaths[0]`).
- **Project identity** (`src/project-resolver.ts`, `resolveProject(dir) → Project | null`): git toplevel (or the folder itself), realpath'd, gives the legacy tag `proj_<sanitized-basename>_<sha256(rootDir)[:6]>`, which is still every repository's tag, because **the memory server cannot re-tag documents** (`PATCH /v3/documents/:id` ignores `containerTags`; `POST /v3/container-tags/merge` fails in `WORKFLOW_ENGINE=direct`). Never change how that tag is derived: it would orphan the stored memories. Clones and worktrees of one `origin` remote are linked in `data/projects.json` (`{ "<normalized remote>": { tag, also: [...] } }`): they write to `tag` (`Project.containerTag`) and read `tag` plus `also` (`Project.readTags`), so earlier memories of every clone stay visible. A repository seen for the first time registers itself; `bun run link-projects` seeds the registry for clones that already hold memories. A missing or corrupt registry only costs sharing. `null` (no project) means: ignored by `SUPERMEMORY_IGNORE`, `$HOME`, or a non-git folder holding git repositories within two levels (a "workspace container"). Hooks then recall nothing (`start` injects one hint line), drop `stop`/`compact`, and route a `change` to the repository that owns the touched file.
- **API key:** `SUPERMEMORY_API_KEY=sm_local_key` is a placeholder. The client then falls back to the server-generated `data/current/api-key` (the active store's; the server also auto-applies its key to unauthenticated localhost requests).
- **Recall is newest-first listing, not vector search:** `start` calls `POST /v3/documents/list` (sorted by `createdAt`), picks per-type budgets from `RECALL` (by `metadata.type`: `session_summary` / `change_observation`), then fetches full content with `GET /v3/documents/:id`. The listing includes documents still processing, so writes from other agents are visible immediately, and takes `readTags` as a list. `start` also appends the server-extracted facts from `POST /v4/profile` (all `static`, newest `PROFILE_FACTS` of `dynamic`). `/v4/search` and `/v4/profile` are single-space (two tags answer 400), so `SupermemoryClient.search`/`profile` call once per tag in parallel and merge.
- **Per-prompt hybrid search:** `sync` sends the event's `prompt` (all three agents) to `POST /v4/search` with `searchMode: "hybrid"` (extracted memories + raw document chunks, the chunks covering documents whose extraction hasn't finished). `pickHits` drops hits from the same session or already injected into it (ids in `$TMPDIR/supermemory-sync/<session>.seen`) and keeps at most `MAX_CHUNKS` chunks, one per document. There is no client-side score threshold: with English (translated) queries or multilingual embeddings the server returns nothing for unrelated chit-chat. Remote embedding models add ~0.5-1.5s per search; translating a non-English prompt adds ~1-2s. Prompts under 3 words are skipped to save the call.
- **Translation (`TRANSLATE_MODEL`):** for English-only embeddings, `toEnglish()` translates the `sync` prompt (8s timeout) and the `stop` summary (12s) through a 9router chat call (`.env`'s `OPENAI_BASE_URL`, `stream: false`) before search/save. `isEnglish()` (stopword ratio) skips English text without a call. Change notes and compaction summaries are never translated (per-tool latency, hook timeout; server extraction writes English memories anyway). Any failure returns the original text. Empty `TRANSLATE_MODEL` disables it (multilingual embedding models).
- **Feedback-loop guard:** `stripContext()` removes quoted `<supermemory-context>` blocks (identified by `CONTEXT_HEADER`) both before saving and when recalling. Keep the header text stable.
- **Server endpoints used:** `POST /v3/documents`, `POST /v3/documents/list`, `GET /v3/documents/:id`, `POST /v4/search` (hybrid, `sync`), `POST /v4/profile` (`start`), `POST /v3/search` (only `test-memory.ts`), and `GET /v3/search/spaces` (health). The shell scripts probe `POST /v4/search`. Manual cleanup only (see README, "Menghapus Dokumen Satu Container Tag"): `DELETE /v3/documents/:id` via `client.request`, which returns 409 "Document is still processing" until extraction finishes.

## Invariants when editing hooks

- **Never block or break the agent.** `bin/supermemory-hook.ts` swallows all errors (logging them to the hook log) and exits 0. Keep it that way.
- **Stdout is the injection channel.** For `claude-code` and `opencode`, whatever `start` prints becomes model context. Never `console.log` diagnostics; use `log()`.
- **Only `runHook` writes stdout.** Handlers return the context string instead of printing; `adapter.render` shapes it. Antigravity always gets a JSON object (`{}`, or `{"injectSteps":[{"systemMessage":{"systemMessage": ...}}]}`; `ephemeralMessage` is deprecated and was re-sent on every model call); the bin's catch prints the adapter's empty output (`{}` for agy) on errors.
- **Hooks must run with `--env-file=<repo>/.env`.** Bun auto-loads `.env` from the working directory, which for a hook is the _user's_ project; `--env-file` loads only ours.
- **The installer writes absolute paths** (bun from `Bun.which("bun")`, a stable symlink such as `/opt/homebrew/bin/bun`, never `process.execPath`, whose versioned Homebrew Cellar dir disappears on `brew upgrade bun` and silently breaks every hook; GUI-launched agents may lack `~/.bun/bin` in PATH; plus `bin/supermemory-hook.ts`) into `~/.claude/settings.json` and `~/.gemini/config/hooks.json`. Edits to `src/` take effect immediately for those agents. It finds and replaces its own entries by the `MARKER` regex (`supermemory-hook.(js|ts)`), and backs up each config as `.bak-<timestamp>` before writing. The configs carry only the command, never a port, URL, model or key, so a `.env` change needs no reinstall. The installer never touches other tools' entries (claude-mem was removed by hand from `~/.gemini/settings.json` and agy's `mcp_config.json`). `antigravityHooks()` and `pluginSource()` are exported pure builders; the CLI part runs under `import.meta.main`.
- **`src/opencode-plugin.ts` is a template in OpenCode v2 format** (default-exported `{ id, setup(ctx) }`, no package import; v1's `export const X: Plugin = async () => ({...})` fails to load with "Plugin must export a default definition"). The installer copies it to `~/.config/opencode/plugins/supermemory-local.ts` (removing the old `.js`) and rewrites the `const HOOK_CMD = [...];` statement with a regex, so keep that declaration shape (no `;` inside). The plugin runs inside OpenCode's shared server process, so it never calls memory code directly: it spawns the hook with a 15 s kill timer, reads each session's directory from `ctx.session.get()` (`ctx.location` is the plugin instance's) and does not await `change`. Plugin changes need `bun run install-hooks opencode`, and Zentty copies plugins at launch, so reopen its panes. Do not register the plugin in `opencode.json`, because it would load twice. `src/opencode-plugin.test.ts` runs it against a fake `ctx` shaped like the fixtures.
- **`src/llm-proxy.ts` must sit between supermemory-server and 9router.** Supermemory's LLM calls (`response_format: json_object`, and tool calling for the memory agent) omit `stream`, and 9router answers with SSE chunks when `stream` is missing, so every document fails with "Invalid JSON response". The proxy sets `"stream": false` when unset (chat), fills `dimensions` from `SUPERMEMORY_EMBEDDING_DIMENSIONS` on `/embeddings` (the server only sends it for `text-embedding-3-*`, and Jina v4's 2048 / Gemini's 3072 defaults exceed pgvector's 2000 limit; the `openai-compatible` embedding provider reaches the proxy through the server's `OPENAI_BASE_URL`), adds `usage.prompt_tokens` to `/embeddings` responses that only carry `total_tokens` (Jina; the server's OpenAI schema check otherwise rejects them as "Invalid JSON response" and documents stay in `embedding` until the hourly retry cron), drops the stale `content-length`/`content-encoding` headers, and runs `Bun.serve` with `idleTimeout: 0` (Bun's 10s default would cut the ~50-110s 9router calls). `scripts/run.sh` runs it (`LLM_PROXY_PORT`, default 20129) and points the server's `OPENAI_BASE_URL` at it; the upstream is `llmUpstream` from `src/config.ts` (`.env`'s `OPENAI_BASE_URL`, falling back to `http://127.0.0.1:$NINEROUTER_PORT/v1`). Extraction depends on `OPENAI_MODEL` working through 9router: a combo with a dead member fails calls (`model not found`, seen as 400 in `data/llm-proxy.log`), the document ends `failed` and the server's hourly cron retries it. `bun run status` shows the recent failure rate and warns above 10%; `supermemory-server doctor` checks the model.

- **`src/zed-adapter.ts` is independent of supermemory.** It serves Zed's `open_ai_compatible_api` edit predictions: legacy `POST /v1/completions` (`{prompt}`) becomes a 9router `/chat/completions` call (9router has no `/completions` and ignores `prompt`, so Gemini 400s on empty `contents`). It uses `.env`'s `OPENAI_BASE_URL` + `OPENAI_API_KEY` (Zed's Authorization header only as fallback), sends `reasoning_effort` (`ZED_ADAPTER_REASONING_EFFORT`, default `none`), and `cleanText` unwraps ``` fences, applies `stop` locally and re-adds the zeta `<|editable_region_start|>`/`<|editable_region_end|>` markers when the chat model drops them. `scripts/run.sh` runs it (`ZED_ADAPTER_PORT`, default 20130) under its own LaunchAgent.

- **`src/stack.ts` + `bin/stack.ts` (stack controller behind `bun run start|stop|restart|status|logs`).** Pure decision logic (`parseCommand`, `orderTargets`, `descendants`, `parseLaunchdPid`, `parseLsofHolder`, `renderPlist`, `summarizeServers`, `loadConfig`) is unit-tested in `src/stack.test.ts`; launchctl/lsof/ps/HTTP side effects go through Bun Shell `$` with `.nothrow().quiet()`. Invariants:
  - **Never SIGKILL, never `bootout`/`unload` `com.9router.autostart`.** `stop --9router` captures the LaunchAgent pid's descendant tree first (next-server runs in its own process group and holds :20128), sends `launchctl kill SIGTERM`, then SIGTERM only to captured descendants still alive, and succeeds only when the port is free. A port holder not descended from that pid is named, never signalled. Start uses `kickstart` without `-k`.
  - mcpm-gateway (`MCPM_GATEWAY_DIR`, default `../mcpm-gateway`) is started/stopped **only through its `gateway.sh`**, never edited; its exit codes are not trusted (port 6276 + label `com.mcpm.gateway` decide). No `gateway.sh` → gateway steps are skipped, not failed. `restart` without selectors never touches the gateway.
  - Settings come from `src/config.ts` (the stack's `loadConfig` only adds the launchd paths); `scripts/env.sh` evals `bun src/config.ts --shell`, so there is no second copy of any default. `src/health.ts` holds the pure parsers behind status's agent-integration lines. `renderPlist` must keep producing the exact text of the already-loaded memory plists; start skips loaded labels and never rewrites them.
  - Exit codes: 0 ok, 1 a selected step failed (9router start problems are warnings only), 2 usage error before any action.
- **`src/mcp-server.ts` + `bin/supermemory-mcp.ts` (stdio MCP server, tools `search`, `add`, `profile`).** Hand-written newline-delimited JSON-RPC to keep the runtime dependency-free; started by the MCP client (`bun --env-file=<repo>/.env bin/supermemory-mcp.ts`), not launchd. stdout is protocol-only, so never `console.log` from anything it imports; diagnostics go through `log()`. `project_path` → `resolveProject()` gives the hooks' project, so both share memory (search/profile read every tag in `readTags`, one call per tag; `add` writes `containerTag`); a path with no project (container, `$HOME`, ignored) is a tool error naming the repositories inside. Tools call `client.request` directly because `client.search`/`profile` turn failures into empty results. The client is built per call: this process outlives server restarts and the api-key belongs to the active store.
- **`src/sessions-*.ts` + `bin/sessions-ui.ts` (Sessions UI) are independent of the hooks and supermemory-server.** They list Claude Code sessions from `~/.claude/projects/<slug>/<sessionId>.jsonl` (live = `~/.claude/sessions/<pid>.json` with an alive pid) and link each to its notes via `metadata.session`. Invariants:
  - `~/.claude` is read-only except an approved delete (a _move_ into `data/sessions-trash/<ts>_<id>/` with a manifest) and restore (a move back). Transcripts are never opened for writing; rename/tags live in `data/sessions-meta.json`.
  - **There is no HTTP route that approves an action.** `POST /api/actions` only creates a pending action; `SessionActions` runs it after the injected `prompt` (a y/N on the server's terminal) answers yes. Don't add an approve/execute route, and keep the typed-id modal as the browser-side speed bump only.
  - Every request passes `Host` (127.0.0.1/localhost + port), `Origin` (state-changing) and per-run `X-Token` checks; the page carries a nonce CSP and writes transcript-derived text with `textContent` only. No `innerHTML`, no external resources, and the page JS must not contain backticks or `${` (it lives in a `String.raw` template).
  - Session and trash ids are validated (UUID / `<ts>_<uuid>`) and paths are built from fixed roots, never from client input. Live sessions are refused at request time and again right before the move.
  - Transcript text never leaves the machine; the only network calls are to the local supermemory server (container tags, a limit, document ids). `SupermemoryClient.request` accepts empty bodies because `DELETE /v3/documents/:id` answers 204.
  - **OpenCode and Antigravity tabs** (`src/sessions-other.ts`, `GET /api/other`): lists open SQLite `mode=ro` (retry `immutable=1` for a WAL db without -wal/-shm, as `agy`'s `conversation_summaries.db`), list columns only, never message bodies. OpenCode v2 lists from `session_v2`; the old `session` table is a stale migrated copy (new sessions never reach it, deletes leave its rows). Rename/tags for both agents go to the sidecar under `opencode:<id>` / `antigravity:<id>` keys (Claude keys stay bare ids). Antigravity has no delete.
  - **OpenCode delete/restore never writes SQL.** The db holds two table generations that only OpenCode keeps consistent, so changes go through its CLI (`src/opencode-cli.ts`: `session export|delete|import --standalone`, real binary, Zentty's wrapper skipped). Order is fixed: refuse while any `opencode` process runs (request time and again before executing; fail closed if `ps` fails) → export the session **and all descendants** (the CLI deletes children too) into `data/opencode-trash/<ts>_<id>.json` (0600, re-read) → `session delete` → verify the session is gone. Never remove a backup on a failure path (a stale read could make a successful delete look failed). Restore imports parent first and only what is still missing, and removes the backup only after the whole family is back. Don't run several `opencode` standalone commands in parallel (they fight over readiness); the code is sequential.
  - Run in the foreground by design (`bun run sessions`), not under launchd; `bin/sessions-ui.ts` refuses to start without a TTY.

## Conventions

- **Configuration is one table:** `src/config.ts` (`DEFAULTS` + `loadConfig`/`currentConfig`) is the only place that knows a setting or its default; `.env` is the only file a user edits and `.env.example` must document every key (a test checks it). Never write `process.env.X || 'literal'` elsewhere. `SUPERMEMORY_IGNORE` (regex on the working directory) makes every hook skip a folder.
- Deliberate shortcuts are marked with `// ponytail:` comments, for example the read-only command heuristic.
- `data/` and `.env` are gitignored. **One store per embedding model:** the server locks its data dir to the provider/model/dimensions/endpoint that first embedded into it (`embedding-plan.json`) and refuses to boot on a mismatch, so `scripts/run.sh` points `SUPERMEMORY_DATA_DIR` at `data/stores/<model>-<dims>d` (name from `SUPERMEMORY_EMBEDDING_MODEL` + `_DIMENSIONS`) and symlinks `data/current` to it. Switching embedding models is edit `.env` + `bun run restart`; each model keeps its own memories. Logs stay in `data/`. Reset the active model's memory with `rm -rf "data/$(readlink data/current)"`. Changing `LLM_PROXY_PORT` breaks existing stores (the endpoint is locked too). The README section "Mengganti Model" has the full procedure for embedding and LLM model changes.
